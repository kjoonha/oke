# PM: experiment job

`output: result` for a git job (`$OKE status`, `jobs.<job>.output`): what the job hands over is a run's outputs and what they show, not a change to keep. Example: change one line, run the simulation, read its output. Nothing is committed: the result stays uncommitted where the job made it. Plan and execute as usual, with these differences.

Plan:
- Record the output while the job plans: `$OKE job output <job> result` (before you report the plan, on every plan and replan; it refuses once the job made something or was delivered).
- Size `normal` or `large`, never `small`: a run can take long, and only a worker pane waits for it (the worker skill's long-run rule). `$OKE job output <job> result` raises a `small` job to `normal` (its output then shows `size`): change it in Approach too.
- OKe chooses where the result is made (`jobs.<job>.workspace` in `$OKE status` once the plan goes to the user): in place, the edit and the outputs stay uncommitted in the user's checkout after the job is done (the approval says so). A `Results: <path>, <path>` line under `## Workspace` names the output files (optional: without it the job's changed files are its result).
- Steps: the temporary edit, the command that runs, and which output files to keep.
- Acceptance criteria: what the result has to show, or that the run finished and its outputs answer the question. A run whose outputs show a failure can still meet them when the job asked what happens.
- Check command: the command that runs the experiment.

Execute:
- Step 1 (the worktree, when `workspace` is `worktree`) as usual.
- The worker works with `commit: no`. Its Instruction starts with `output: result`: the worker runs `oke check <job>` once, which is the run (it records it with its exit code; nothing runs on the base, and the run's outputs are `check_left`: never part of the edit, never committed). It reports where the outputs are (paths inside its `cwd`) and what they show. Do not run `$OKE check` again unless the edit changed since: that runs the experiment again.
- Never commit the edit, before the review or between rounds: it stays uncommitted. The reviewer's assignment is `$OKE_HOME/jobs/<job>/<job>-rv/assignment.md`, as in **Review** (role `reviewer`, `cwd` the worker's; a reviewer pane at size large, the review subagent at normal, its answer saved to `report.md` next to the assignment: `job phase done` reads it there), but with no `commit:` or `tree:`. Size large: `$OKE spawn <that file> --split-from <worker pane>`, write the job's report as `waiting` (`on: <job>-rv`), start `$OKE wait <job>-rv --report <its folder>/report.md --seq <its seq>` in the background, end your turn. Size normal: the review subagent (Job size), its answer saved to that `report.md`. Its Instruction starts with `output: result`, names the edit (the `diff` command `$OKE job tree <job>` prints: only the job's own changes, never the user's other uncommitted files; a reviewer pane runs it plain in its `cwd`, the review subagent with `git -C <cwd>`; new files of the edit, `??` in `git status --short`, listed by name to read whole) and the output files to read, and asks: do the outputs meet the Acceptance criteria, and did the run use the planned edit and nothing else?
- `verdict: pass`: run `$OKE job deliver <job>`. For a result it commits nothing: it checks that `$OKE check` recorded a run of the edit as it is now (its exit code is the reviewer's to grade) and prints `"result": "in_place"`, the `path` and the `results` files (exit 1: the edit changed since the run: run `$OKE check <job>` again, then deliver). Close the worker and reviewer (`$OKE close <pane> <pane>`). Never commit, and never remove a worktree: it holds the outputs and stays until the user says to remove it. `changes`: a new round as usual. The orchestrator's `job phase done` refuses until the reviewer passed the latest result.
- Log the wiki (`$OKE wiki write` or `$OKE wiki log --job <job> --note none`), then report `done`: the result (what the outputs show) in Summary, the output files and the `path` deliver printed.
