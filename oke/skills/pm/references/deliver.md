# PM: deliver a reviewed job

You come here from `verdict: pass` under **Review** in SKILL.md (not for an experiment). OKe never merges into the user's branch: the job hands over its own branch `oke/<job>`, brought onto the latest base branch and checked there. The user merges it. A job in place (the main checkout, or a linked worktree the user named) gets its reviewed changes committed there, on the branch that checkout is on, instead. Only the job's own changes are committed: the user's uncommitted files from before the job stay uncommitted and untouched. A plan's `## Commits` section (`- <message>: <path>, <path>`, one group may be `rest`) makes one commit per group, in order; without it, one commit.

Job size: where the steps below instruct the worker, a small job calls the work subagent again; where they instruct the reviewer, small and normal jobs call the review subagent again.

1. Run `$OKE job deliver <job>` (never `git merge`, `git rebase` or `git commit` yourself for this). It checks that the last review passed after the last worker report and answers its current assignment, the branch tip is the commit that review named, the review's `criteria_rev` is the plan's current one, and `$OKE check` passed on that commit (a plan whose Check command is `none (<why>)`: instead, the review graded every acceptance criterion `VERIFIED`; it refuses otherwise, and names the criteria: give the reviewer a new instruction to grade them).
   - Exit 0 (`"result": "delivered"`): the branch is on the latest base branch with a passing check (in place: `"direct": true`, the `commits` it made there). Go to step 3.
   - Exit 5 (`"result": "user_files"`): the job changed files the user had already changed before it began (`files`). Nothing was committed. Report `question` for the job, per file, with the line `asks: user_files` in its block (only the user answers it): include my edits in the job's commit / leave that file out of the commit (both edits stay uncommitted). The orchestrator records the answer (`$OKE job files`) and gives you `kind: answer`. After `include`, step 1 again; after `leave` the job's tree changed: `$OKE check <job>`, a new review with the new `tree:`, then step 1.
   - Exit 4 (`"result": "rebased"`): the base branch had moved on; OKe rebased the branch onto it in the worktree without a conflict, and the change is the reviewed one (same patch id), so the review counts for the new tip `commit`. Write the job's report as `waiting` (`on: check`), run `$OKE check <job>` in the background (no time limit: a long check is normal), end your turn. Check passed: run step 1 again. Check failed (exit 1): give the worker a new instruction with the new failures ("After the rebase onto `<base branch>` the Check command fails: ... Fix it, run the Check command, commit, and report."), then a new review of the new tip, then step 1.
   - Exit 2 (`"result": "conflict"`): the rebase conflicted in `files`; OKe undid it and the branch is as it was. Never resolve conflicts yourself. Climb this ladder:
     1. Give the worker a new instruction, with `commit: yes` in its header from now on: "Rebase `oke/<job>` onto `<base branch>`. Resolve the conflicts so that both changes keep their purpose. Run the Check command again, commit, and report." Write this job's report as `waiting` (`on: <job>-w1`) and wait. A dead worker makes the wait say `gone`: handle it as in the wait table of SKILL.md.
     2. Worker `done`: give the reviewer a new instruction to review the whole `<base branch>...<rebased tip>` range again (a job that continues another: `<review_base>...<rebased tip>`, with `review_base` read from `$OKE status` after the rebase; see **Review** in SKILL.md), with `commit:` set to the rebased tip, and run `$OKE check <job>` on it. `verdict: pass`: step 1 again. `changes`: as in the review rounds.
     3. Worker `question` or `failed`, or it conflicts again after that: report `question` for the job with the conflicting files. The user decides.
   - Exit 1: refused; the message says why. The rebase changed the change (another patch id): the branch is rebased; give the reviewer a new instruction with the `commit:` the message names (a job that continues another: the range `<review_base>...<that commit>`, `review_base` read from `$OKE status` now), run `$OKE check <job>`, then step 1. A review problem (the worker reported after it, the branch moved past its commit, a stale `criteria_rev`, no passing check): fix that as the message says, then step 1. Uncommitted changes the review did not cover: a new review with the `tree:` from `$OKE job tree <job>`, step 1. Changed files no `## Commits` group names, and no `rest` group: report `question` with the files (add them to a group, or add `rest`). No record of the user's files from the job's start: report `question` with `asks: user_files` naming the changed files (`git status --short`): which of them are the job's; only those the user names are committed. Commits in the checkout since the job began: report `question` with `asks: head_moved` naming them (the `commits` OKe printed): did the user make them? On yes the orchestrator accepts them; on no report `failed` for the job naming those commits (never reset them). No passing check after a failure the user may accept: report `question` with `asks: check_accept`. A git repository inside the checkout: have the worker move it out. A main-checkout problem (another branch checked out, a merge in progress), no base branch, or anything else: report `question` for the job with the message. The user decides.
2. A `tree:` review: the same command commits the job's changes (new files included) only when they are exactly the reviewed tree. With a worktree it keeps the worker's commits and commits only what is left. `user_files_kept` lists the user's uncommitted files it left alone: mention them in your report. `"already_in": true`: the change was already there; nothing was committed.
3. Update the wiki from the reports' Learned and fix the pages they marked `wrong` (see **Wiki** in SKILL.md). What holds beyond you as a PM goes into your done report's Learned (shared) instead.
4. Close the worker and reviewer: `$OKE close <pane> <pane>` (the `pane` that `spawn` printed). A pane under `failed` as not found is already closed: fine. Any other `failed` pane: close it once more; if it stays, tell the user which pane to close. Leave the worktree as it is: the user merges from its branch, and removes it (`$OKE job clean <job>`, on the user's word).
5. Report `done` for the job: summary, the Acceptance criteria lines of the review, "the base already failed: N failure lines (warning)" when the last `$OKE check` printed `pre_existing` lines (N counts them, the distinct failure-output lines, not failing tests; name the failing tests the lines show), the delivered `branch` and `commit`, the `base` branch, the worktree path, the number of changed files (`git diff --stat <base>...<branch>`; without a worktree `git show --stat <commit>`), and the workers' Learned. In place say "committed in <path> as <commits>". A job that continues another (`contains` in the output): say that its branch also holds the commits of `<A>`'s branch, so merging it brings both. `"already_in": true`: the base branch holds the branch already; say there is nothing left to merge.
