# PM: deliver a reviewed job

You come here from `verdict: pass` under **Review** in SKILL.md (not for an experiment). OKe never merges into the user's branch: the job hands over its own branch `oke/<job>`, brought onto the latest base branch and checked there. The user merges it. A job without a worktree gets its reviewed changes committed in the main checkout instead.

Job size: where the steps below instruct the worker, a small job calls the work subagent again; where they instruct the reviewer, small and normal jobs call the review subagent again.

1. Run `$OKE job deliver <job>` (never `git merge`, `git rebase` or `git commit` yourself for this). It checks that the last review passed after the last worker report and answers its current assignment, the branch tip is the commit that review named, the review's `criteria_rev` is the plan's current one, and `$OKE check` passed on that commit.
   - Exit 0 (`"result": "delivered"`): the branch is on the latest base branch with a passing check (without a worktree: `"direct": true`, the commit it made in the main checkout). Go to step 3.
   - Exit 4 (`"result": "rebased"`): the base branch had moved on; OKe rebased the branch onto it in the worktree without a conflict, and the change is the reviewed one (same patch id), so the review counts for the new tip `commit`. Write the job's report as `waiting` (`on: check`), run `$OKE check <job>` in the background (no time limit: a long check is normal), end your turn. Check passed: run step 1 again. Check failed (exit 1): give the worker a new instruction with the new failures ("After the rebase onto `<base branch>` the Check command fails: ... Fix it, run the Check command, commit, and report."), then a new review of the new tip, then step 1.
   - Exit 2 (`"result": "conflict"`): the rebase conflicted in `files`; OKe undid it and the branch is as it was. Never resolve conflicts yourself. Climb this ladder:
     1. Give the worker a new instruction, with `commit: yes` in its header from now on: "Rebase `oke/<job>` onto `<base branch>`. Resolve the conflicts so that both changes keep their purpose. Run the Check command again, commit, and report." Write this job's report as `waiting` and wait. A dead worker makes the wait say `gone`: handle it as in the wait table of SKILL.md.
     2. Worker `done`: give the reviewer a new instruction to review the whole `<base branch>...<rebased tip>` range again (a job that continues another: `<review_base>...<rebased tip>`, with `review_base` read from `$OKE status` after the rebase; see **Review** in SKILL.md), with `commit:` set to the rebased tip, and run `$OKE check <job>` on it. `verdict: pass`: step 1 again. `changes`: as in the review rounds.
     3. Worker `question` or `failed`, or it conflicts again after that: report `question` for the job with the conflicting files. The user decides.
   - Exit 1: refused; the message says why. The rebase changed the change (another patch id): the branch is rebased; give the reviewer a new instruction with the `commit:` the message names (a job that continues another: the range `<review_base>...<that commit>`, `review_base` read from `$OKE status` now), run `$OKE check <job>`, then step 1. A review problem (the worker reported after it, the branch moved past its commit, a stale `criteria_rev`, no passing check): fix that as the message says, then step 1. Uncommitted changes in the worktree: commit the job's own (as in **Review**), get a new review, step 1. A main-checkout problem (another branch checked out, a merge in progress), no base branch, or anything else: report `question` for the job with the message. The user decides.
2. A job without a worktree (`tree:` review): the same command commits the main checkout's tracked changes plus the new files you staged, only when they are exactly the reviewed tree. It names untracked files it left (`left_untracked`): mention them in your report. `"already_in": true`: the change was already there; nothing was committed.
3. Update the wiki from the reports' Learned and fix the pages they marked `wrong` (see **Wiki** in SKILL.md). What holds beyond you as a PM goes into your done report's Learned (shared) instead.
4. Close the worker and reviewer: `$OKE close <pane> <pane>` (the `pane` that `spawn` printed). A pane under `failed` as not found is already closed: fine. Any other `failed` pane: close it once more; if it stays, tell the user which pane to close. Leave the worktree as it is: the user merges from its branch, and removes it (`$OKE job clean <job>`, on the user's word).
5. Report `done` for the job: summary, the Acceptance criteria lines of the review, "the base branch already failed: N failure lines (warning)" when `$OKE_HOME/jobs/<job>/baseline.json` has signatures (N counts its `signatures`, the distinct failure-output lines, not failing tests; name the failing tests the lines show), the delivered `branch` and `commit`, the `base` branch, the worktree path, the number of changed files (`git diff --stat <base>...<branch>`; without a worktree `git show --stat <commit>`), and the workers' Learned. Without a worktree say "committed in the main checkout as <commit>". A job that continues another (`contains` in the output): say that its branch also holds the commits of `<A>`'s branch, so merging it brings both. `"already_in": true`: the base branch holds the branch already; say there is nothing left to merge.
