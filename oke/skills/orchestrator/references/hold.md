# Orchestrator: jobs on hold

The user sets a job aside without giving it up, often after a crash ("leave it for now", "do the other thing first"). A held job stays in `$OKE status` (class `held`, `held` is the reason) with its worktree and branch, but nothing runs for it: OKe does not revive its PM or agents for it, the PM's wait does not watch it, and the start procedure does not ask about it again.

- Hold: `$OKE job hold <job> --reason "<why>"`. It closes the job's worker and reviewer, drops its queued messages, and queues a notice telling the PM to leave the job alone. If the PM is alive and no wait of it runs, start one so the notice goes in. It prints the closes as cancel does: `not_closed` children: run `job hold` again (on a held job it only retries the closes); if they stay, tell the user which panes to close. `refused` children: do not run it again; tell the user which panes to close. It refuses a job that is done or failed, a direct job that has started its work, and a job that has started its work in the main checkout (its plan has no worktree and there is no branch `oke/<job>`: its edits sit in the user's checkout; a job that never reached `working` can still be held). Once a job has started, it refuses a folder job ("changes its folder in place") and a git job that works in the main checkout without a branch ("works in the main checkout"): tell the user it cannot be set aside, and ask with `AskUserQuestion`: let it finish / cancel it (see "Giving up").
- When `job hold` refuses (wherever hold was offered: the start question, a `gone`): tell the user why in one line and ask again at once with only resume, or cancel and archive when the message says so. Never offer hold again for that job, and never ask the same question twice in a row: the user's answer decides.
- Continue ("continue <job>", "pick up <job> again"): `$OKE job unhold <job>`. It prints `pm` and `pm_job_dir`. A job in `intake` has no PM assignment: send nothing, revive nothing, and resume its interview ("Interview" under Intake; never run `job new` again: the job exists). A job a PM split off (still in `intake`, with no PM assignment) needs no interview: its `split` item comes back in `$OKE pending`; handle it there. The rest of this rule is for later phases. Otherwise, if the PM is dead (`$OKE status`: `pms[<pm>].pm` is `dead`), `$OKE revive <pm> --reset`: it tells the PM to re-read that job's assignment. If the PM is alive: `$OKE send <pm> --job <job> "Job <job>: back from hold. Re-read <pm_job_dir>/assignment.md and continue it."` Always send it: the PM leaves the job alone until it gets this message. For a job in `awaiting_approval` add "It waits on the user: act on its next assignment.", then run the queue, which asks the user again. Then start its wait.
- Drop it for good: cancel and archive it as in "Giving up".
