# Orchestrator: rare queue items

- `unassigned`: you set the job's phase to `working` (an approval, an `after_ready`, a curate start) and were compacted before writing its assignment. Its report is still the plan's, not work. Write the assignment the phase was set for (`kind: execute` with `size: <size>, output: <output>`, both from `$OKE status`, after an approval or `after_ready`; `kind: curate` for a curation; `kind: research` for another research job) and do steps 2 to 6 of "Give the job to the PM" (step 3 changes nothing: the phase is already `working`). No question.
- `unsent`: you wrote that job's assignment but never sent the message (you were compacted in between). Read the assignment's `kind` and do steps 3 to 6 of "Give the job to the PM" now: set the phase that kind belongs to (see "Flow"), make sure the PM runs, send, wait. For `kind: cancel` (an older OKe wrote it), cancel the job as in "Giving up" instead. For `kind: dialog`, the key may not have gone to the child yet: read the child's screen (`$OKE read <child>`). Send the key only if it still shows the same dialog as the PM's report; a different dialog is a new one the user has not seen, so send nothing and let the PM report it. No question.
- `silent`: the PM did not report on that job even after a nudge. Ask: go to the PM pane (`$OKE attach <pm>`, then `$OKE job defer <job>`) / send the same step again (steps 2 to 6 of "Give the job to the PM" with the same Instruction: the new seq gives the PM a fresh start) / give up (see "Giving up").
- `peer`: the PMs in the item's `peers` were asked about the impact of a change and never answered. Ask: proceed as if there is no impact / go to that PM's pane (`$OKE attach <pm>`, then `$OKE job defer <job>`) / give up the job (see "Giving up"). For "proceed": give `<job>`'s PM `kind: answer` "<those PMs> did not answer: plan as if there is no impact" (steps 2 to 6 of "Give the job to the PM").
